An EPUB opens and its chapters read normally, but the table-of-contents button is empty in one reading app. In another app, the same book has a complete chapter menu. Does that mean the EPUB is broken, or that the first reader is at fault? Neither conclusion follows from the symptom alone. First establish whether the two apps opened the same file revision, whether the EPUB actually contains a navigation structure, and whether the reader is displaying that structure.

This guide is for people troubleshooting a missing reader-generated EPUB chapter menu, not for deciding how chapters should be ordered in a manuscript. It offers a read-only investigation before any repair. The examples below are invented teaching scenarios, not reports of actual defects in named reading products.

Three different things can look like a table of contents

An ebook can contain a visible page titled “Contents,” a navigation structure that a reading app uses to build its own chapter menu, and a default sequence in which chapters appear when you turn pages. Those are not interchangeable. A beautifully formatted contents page could consist of ordinary text; its existence does not demonstrate that the app can build a navigation menu from it. Conversely, a reading app can show a navigation menu even if no contents page appears as part of the story.

The W3C EPUB 3.3 specification requires an EPUB navigation document. The publication's package document identifies that resource in its manifest with the nav property, and the navigation document must contain exactly one toc navigation element. The package's spine is a different structure: it specifies the default reading order. That separation explains why a reader can sometimes progress through every chapter while displaying a poor or apparently missing chapter list.

For EPUB 3 reading systems, the W3C reading-systems specification says conforming readers must process the navigation document and give users access to its table-of-contents links and headings. The exact place a product puts its contents control is a user-interface detail. A hidden menu, an old imported copy, a malformed package or incomplete reader support can produce superficially similar reports. Treat them as hypotheses to test, not as confirmed causes.

Confirm the file before interpreting the app's behavior

Save the original EPUB somewhere safe. Give a working copy a conspicuous filename such as field-guide-export-B.epub. Check the file size, export date and, if your workflow supports it, a SHA-256 digest for the copy you open on each device. Identical filenames are weak evidence: a reader may have imported an older version into its library, or a sync process may have retained the previous publication.

In each app, locate its actual contents or navigation control rather than relying on a page headed “Contents” inside the book. Note whether a chapter list appears, whether the app collapses nested entries, whether search can find the opening words of a supposedly missing chapter, and whether consecutive page turns reach that chapter. Record the reader name, version and file revision. Do not erase an annotated or highlighted library copy just to test a fresh import; protect its annotations first.

If one reading system shows the menu and another does not, a controlled fresh import of the exact same test copy helps isolate an app or library-state difference. It does not prove an implementation bug. If both lack the menu, examine the package structure next. If a contents list appears but its links jump to the wrong sections, that is a different failure requiring target-by-target checks.

Inspect the EPUB package without changing the master

An EPUB is a packaged publication, and many EPUBs can be inspected using a ZIP-aware archive viewer. Work from a duplicate, not the only manuscript or ebook. First locate the package document using META-INF/container.xml; do not assume every EPUB uses the same folder name or package filename. The package document normally has an .opf extension. A file listing may be enough for an initial inspection, but filenames alone do not establish the document roles.

Inside that package document, identify the manifest item whose properties value includes nav. Follow its relative href to the navigation XHTML file. Inspect whether that file contains a nav element with epub:type set to toc, along with meaningful links to the intended sections. The precise paths and element IDs vary by publication. A correct-looking navigation file can still contain references to missing or misnamed targets, so examine the destinations rather than only counting links.

Next compare the spine item references with the chapter files. If the chapter content remains available in the spine but the navigation links are incomplete, you have evidence of a navigation-specific problem rather than automatically missing book text. Do not “fix” that by moving files around inside the ZIP: changing a path without updating the references can create new failures, and repackaging EPUB has its own requirements.

Older EPUB 2 material may include an NCX navigation file, and some workflows generate both forms. Finding an NCX does not, by itself, prove that a current EPUB 3 navigation document is correctly declared. Determine which EPUB version the package represents and validate it using the applicable rules, rather than guessing from file extensions. Avoid searching private manuscripts with online archive viewers unless you have verified the service's privacy practices.

Example 1: the two readers imported different revisions

Imagine an independently authored field handbook with twelve sections. Its editor exports version A on Monday, then exports version B on Tuesday after rebuilding the table of contents. A desktop reader imports B and displays all twelve entries. A phone reader still shows six entries. Both library items are called Field Handbook, so the editor initially assumes that the phone fails to process the EPUB navigation document.

The editor compares the actual imported files rather than their display titles. The phone's file is older and has a different checksum. After preserving annotations, the editor tests a newly named copy of version B in a separate library entry. Its twelve chapters now appear. This fictional outcome would point to a stale import or sync mismatch in this case; it would not establish that every missing contents menu is a cache problem. The practical lesson is that same title does not mean same bytes.

Example 2: every chapter is readable, but the navigation file is wrong

Now imagine a fictional community cookbook with sections for soups, bread and desserts. The exported EPUB lets readers turn from soups to bread to desserts. But its reading-app menu lists only the introduction. On inspecting a copy of the package, the publisher finds a navigation document with a toc section containing only that one link, even though the spine includes the other chapters.

The publisher runs the validator and reviews its messages, then returns to the source project's navigation configuration and regenerates the EPUB. This is more defensible than hand-editing the distributed file and losing the fix on the next export. Even if the initial one-link navigation structure happens to pass a structural validator, the content is editorially incomplete. The publisher must still compare the menu with the expected recipe sections and click every entry in at least one appropriate reader.

Use EPUBCheck, then do a real navigation test

The official EPUBCheck instructions describe checking a packaged file with the command shown below after EPUBCheck has been installed. Run it on a local, clearly identified copy. The exact invocation can differ if you downloaded the Java distribution instead of installing a command-line wrapper.

epubcheck field-guide-export-B.epub

Read the full result, including errors and warnings. EPUBCheck can identify many specification-conformance issues, including malformed references, but it cannot tell whether all intended chapter headings were actually included, nor whether a particular reader presents a discoverable navigation button. A clean validation report is therefore necessary evidence in many publishing workflows, not a guarantee of perfect navigation or universal device compatibility.

If EPUBCheck reports an error, follow its specific message back to the authoring or export workflow. If validation is clean but the reader menu is absent, compare reader versions, try a second conforming reader, repeat the controlled import and document the difference. Do not automatically attribute the issue to either side without a reproducible test and the exact file revision.

A safe, repeatable six-step diagnosis

  1. Preserve: keep the manuscript, original EPUB and any reader annotations; use copies for inspection.
  2. Identify: record the exact EPUB revision opened by each reader, not just its library title.
  3. Separate: check the app's contents menu, any visible contents page, and chapter-to-chapter reading order independently.
  4. Inspect: locate the package document, manifest navigation item, toc links and spine; record what is present without editing it.
  5. Validate: run EPUBCheck and investigate actual errors or warnings, while keeping editorial expectations in a separate checklist.
  6. Regenerate and compare: repair the source or supported export settings, produce a new filename, revalidate, and retest every intended link in the target readers.

For a useful support report, include the EPUB version and validator summary, whether the missing section exists in ordinary reading, whether the contents menu is empty or merely partial, the reader versions and the smallest reproducible sample you have permission to share. Avoid sending an entire unpublished or confidential book when a short original test manuscript will demonstrate the same symptom.
