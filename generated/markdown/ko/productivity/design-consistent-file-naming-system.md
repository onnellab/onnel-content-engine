# 찾기 쉬운 파일명 규칙을 만드는 방법

## 질문

파일이 늘어나도 일관되게 사용할 파일명 규칙은 어떻게 만들까요?

## 짧은 답변

뜻이 분명한 몇 개의 항목을 정해 항상 같은 순서로 써요. 바뀌지 않는 식별 정보, 의미를 정한 날짜, 자릿수를 맞춘 번호, 승인 상태와 구분한 수정본 번호를 짧은 예시로 기록하고 실제 파일 다섯 개에 적용해 봐요.

파일명에 모든 정보를 넣을 필요는 없어요. 목록에서 대상을 알아보고, 비슷한 파일을 구별하고, 원하는 순서로 찾을 수 있을 정도면 충분해요. 이름을 만드는 사람이 매번 새롭게 판단해야 한다면 규칙을 더 단순하게 다듬어 봐요.

## 작은 규칙부터 정해요

파일명의 ‘항목’은 식별 정보나 날짜처럼 한 가지 뜻을 담는 부분이에요. 파일명 규칙은 어떤 항목을 어떤 순서로 쓰고, 무엇으로 구분할지 정한 약속이에요. 예를 들어 다음 이름은 사람이 직접 만든 설명용 예시예요. 특정 앱이 이 조합을 만들어 준다는 뜻은 아니에요.

`atlas_2026-10-05_notes_003_v02.txt`

| 항목 | 이 예시에서의 뜻 |
| --- | --- |
| `atlas` | 가상의 프로젝트 Atlas를 나타내는 고정 식별 정보 |
| `2026-10-05` | 회의가 열린 날짜인 2026년 10월 5일 |
| `notes` | 문서 종류인 회의록 |
| `003` | 이 회의의 회의록 묶음 안에서 사용하는 항목 번호 003 |
| `v02` | 저장한 수정본 번호 02 |
| `.txt` | 파일 확장자 |

이 예시의 순서는 ‘프로젝트_회의 날짜_문서 종류_항목 번호_수정본’이에요. 다른 업무에서는 회의 날짜 대신 촬영일이나 발행일을 쓸 수 있지만, 같은 자리의 뜻을 파일마다 바꾸지는 않아요. 항목 번호와 수정본 번호도 역할이 달라요. 전자는 어떤 항목인지, 후자는 그 항목의 어느 수정본인지를 알려 줘요.

## 권장 워크플로

1. **가장 먼저 찾는 기준을 맨 앞에 놓아요.**

   보통 프로젝트 이름부터 떠올린다면 프로젝트를 앞에 둬요. 여러 프로젝트를 날짜별로 훑어보는 일이 많다면 날짜를 먼저 쓰는 편이 맞을 수 있어요. 일반적인 문자순 정렬에서 프로젝트가 앞에 있으면 각 프로젝트 안에서 날짜순으로 모여요. 전체 프로젝트가 하나의 날짜순으로 섞여 정렬되는 것은 아니에요. 실제로 파일을 찾는 질문 하나를 기준으로 순서를 정해요.

2. **날짜 형식과 날짜의 뜻을 함께 정해요.**

   `YYYY-MM-DD`처럼 연도 네 자리, 월과 일 두 자리를 사용해요. `2026-10-05`는 월과 일을 혼동하기 쉬운 축약형보다 읽기 명확해요. 이어서 이 날짜가 행사일, 촬영일, 발행일 중 무엇인지 적어 둬요. 다운로드한 날과 문서가 발행된 날을 같은 항목에 섞으면 이름만 보고 구별하기 어려워요. 날짜를 모르면 정해 둔 방식에 따라 생략하거나 `unknown` 같은 미상 표시를 써요. 자리를 채우려고 오늘 날짜를 대신 넣지는 않아요.

3. **쉽게 바뀌지 않는 식별 정보를 골라요.**

   짧은 프로젝트 이름이나 기록 번호처럼 대상을 계속 가리킬 수 있는 값을 써요. 임시 담당자 이름이나 `urgent` 같은 표현은 상황이 바뀌면 식별 정보로서 도움이 줄어들어요. 이름이 비슷한 두 프로젝트가 있다면 구별 가능한 약칭을 먼저 정해요. 파일명은 첨부파일 목록이나 공유 링크에 드러날 수 있으므로 개인 정보와 기밀 정보를 불필요하게 넣지 않아요.

4. **번호를 세는 범위와 자릿수를 정해요.**

   번호가 프로젝트 전체에서 이어지는지, 회의마다 다시 시작하는지, 한 작업 묶음 안에서만 쓰이는지 정해요. 예시의 `003`은 해당 회의의 회의록 묶음 안에서 쓰는 번호예요. `001`, `002`, `010`처럼 자릿수를 맞추면 일반적인 문자순 정렬에 도움이 돼요. 숫자를 인식하는 자연 정렬에서는 이미 숫자순으로 보일 수도 있어요. 예상 개수에 맞춰 자릿수를 정하고, 범위를 넘으면 같은 범위의 번호를 일관되게 늘리는 방법을 정해요.

5. **수정본 번호와 승인 상태를 구분해요.**

   `v01`, `v02`를 언제 올릴지 한 문장으로 적어요. 예를 들어 검토용으로 새 내용 묶음을 저장할 때 번호를 올리는 방식이 있어요. 사소한 저장마다 올릴지, 검토본을 낼 때 올릴지는 업무에 맞게 선택하되 일관되게 적용해요. `v03`이라는 이름만으로 검토나 승인이 끝났다고 볼 수는 없어요. 승인 여부는 별도의 합의된 상태나 기록으로 확인해요. `final-final` 같은 이름도 승인 근거가 되지 않아요.

6. **짧은 규칙을 적고 파일 다섯 개로 시험해요.**

   항목 순서, 각 항목의 뜻, 구분자, 선택 항목, 예외 처리 방식을 적어요. 일반 파일, 다른 프로젝트 파일, 번호가 `010`인 항목, 날짜를 모르는 파일, `v02` 수정본처럼 대표 사례 다섯 개를 골라 봐요. 실제 사용하는 파일 관리자와 전달 대상 앱에서 이름 표시, 검색, 정렬, 중복 이름을 확인해요. 날짜를 생략했을 때 남은 항목을 알아볼 수 있는지도 살펴봐요. 대량 적용 전에 작은 묶음에서 규칙의 빈틈을 찾는 단계예요.

## 항목별 역할을 한눈에 확인해요

이 그림의 핵심은 한 항목에 한 가지 뜻을 주는 거예요. 날짜 하나를 회의일과 저장일로 번갈아 쓰거나, 번호 하나로 항목 순서와 수정 차수를 동시에 나타내지 않아요.

## 지키기 쉬운 규칙으로 유지해요

밑줄이나 하이픈 같은 구분자는 일관되게 써요. 예시에서는 항목 사이에 밑줄을, 날짜 안에는 하이픈을 사용했어요. 영문을 소문자로 쓰는 것은 이 예시의 편집상 선택이지 모든 환경의 필수 조건은 아니에요. 받는 시스템에서 허용하는 문자와 이름 길이도 확인해야 해요.

확장자는 보존해요. 이름 끝의 `.txt`를 `.pdf`로 바꾼다고 파일 형식이 변환되지는 않아요. 파일명 규칙은 폴더 구조, 접근 권한, 변경 이력을 대신하지도 않아요. 필요한 정보 중 일부는 폴더나 별도의 기록에 두는 편이 더 적절해요.

규칙을 바꿀 때 기존 보관 파일 전체를 자동으로 다시 이름 짓지는 않아요. 연결된 링크나 다른 사람의 작업 흐름에 영향을 줄 수 있어요. 새 파일부터 적용할지, 검토한 일부 묶음만 바꿀지 먼저 범위를 정해요.

## 자주 묻는 질문

### 모든 파일명에 날짜를 넣어야 하나요?

아니에요. 찾거나 구별하는 데 도움이 될 때만 넣어요. 날짜를 넣는다면 무엇을 나타내는지 정하고, 모르는 날짜를 오늘 날짜로 대신하지 않아요.

### 날짜와 프로젝트 중 무엇을 먼저 쓰나요?

주로 찾는 기준을 먼저 써요. 날짜가 앞이면 전체 날짜순 정렬에, 프로젝트가 앞이면 프로젝트별 묶음에 맞아요. 프로젝트 우선 형식의 날짜순 정렬은 각 프로젝트 안에서 이루어져요.

### `v03`이면 승인된 파일인가요?

아니에요. 정한 규칙에 따른 수정본 번호예요. 승인은 별도의 상태나 기록으로 확인해야 해요.

### Aligna에서 이 예시와 똑같은 형식을 만들 수 있나요?

확인된 것은 여덟 가지 고정 프리셋이에요. 이 글의 전체 조합을 그대로 만들 수 있다는 점은 확인되지 않았어요. 필요한 형식에 맞는 프리셋이 있는지 살펴보고 미리보기로 확인해요.
