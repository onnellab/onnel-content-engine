# 如何建立一致又好找的檔案命名規則

## 問題

如何訂出一套檔案變多後，仍能持續使用的命名規則？

## 簡短回答

選擇少量意思明確的欄位，每次都依固定順序排列。使用穩定的識別資訊、意思清楚的日期、位數一致的序號，以及與核准狀態分開的修訂編號；寫下簡短規則與範例，再用五個具代表性的檔案測試。

檔名不需要裝進所有背景資訊。能在清單中辨認對象、區分相似檔案，並依需要查找，就已經發揮作用。如果每次命名都要重新做許多判斷，可以先考慮減少欄位，而不是增加更多細節。

## 從一套小規則開始

這裡的「欄位」是指檔名中負責表達一種意思的部分，例如專案識別資訊或日期。命名規則則約定使用哪些欄位、各自代表什麼、如何排列，以及用什麼符號分隔。以下是人工設計的說明範例，不代表某個應用程式能產生這個完整組合。

`atlas_2026-10-05_notes_003_v02.txt`

| 欄位 | 在這個範例中的意思 |
| --- | --- |
| `atlas` | 虛構專案 Atlas 的固定識別資訊 |
| `2026-10-05` | 會議日期，也就是 2026 年 10 月 5 日 |
| `notes` | 文件類型：會議紀錄 |
| `003` | 這次會議紀錄集合中的項目編號 003 |
| `v02` | 已儲存修訂稿的編號 02 |
| `.txt` | 檔案的副檔名 |

這個順序是「專案_會議日期_文件類型_項目編號_修訂編號」。003 用來區分集合內的項目，v02 則用來區分同一項目的修訂稿。兩種編號的用途不同，不宜讓同一個數字同時負責這兩件事。

## 建議流程

1. **把最常用的查找依據放在前面。**

   如果通常先想到專案，就先寫專案識別資訊。如果常常跨專案依日期瀏覽，可以把日期放在前面。使用一般文字排序時，專案在前的格式會先按專案分組，再於各專案內依日期排列；不會把所有專案的檔案一起排成日期順序。先想清楚自己比較常問「是哪個專案」，還是「是哪一天」。

2. **一起定義日期格式與日期的意思。**

   採用 `YYYY-MM-DD`，年份四位，月份與日期各兩位，例如 `2026-10-05`。固定格式能避免簡寫造成的月、日順序歧義。也要說明這是活動日期、拍攝日期還是發布日期，不要在同一欄位混用事件日期與儲存日期。日期不明時，依規則省略該欄位，或使用已寫進規則的未知標記，例如 `unknown`。不要為了補滿欄位，就用今天的日期代替。

3. **選擇簡短而穩定的識別資訊。**

   專案簡稱或紀錄編號應持續指向同一個對象。暫時的負責人姓名，或 `urgent` 這類急迫程度描述，會隨情況改變，不適合當主要識別依據。如果兩個專案的簡稱相近，先訂出可以區分的寫法。檔名可能出現在附件清單或分享連結中，因此不要不必要地放入個人資料、客戶隱私或機密內容。

4. **訂好序號的範圍與位數。**

   編號是整個專案持續累加，還是每次會議、每批資料重新開始？把計算範圍寫清楚。範例中的003是在這次會議的紀錄集合內使用。`001`、`002`、`010` 這種補零方式有助於一般文字排序；採用自然排序的應用程式，可能本來就會依數值大小排列。依預估數量選擇位數。若超出原本的範圍，先規劃一致的擴位方式，避免在同一範圍混用不同寬度。

5. **分開管理修訂編號與核准狀態。**

   寫明何時從 `v01` 遞增為 `v02`。例如，可以在儲存一份含有新內容、準備送審的修訂稿時增加編號。每次小改動都增加，或只在產生新的審閱稿時增加，應依工作需要選擇並持續採用。`v03` 只是依約定產生的修訂編號，不能證明檔案已經核准。`final-final` 也不是核准依據。核准情況應由另外約定的狀態或紀錄確認。

6. **寫下簡短規則，用五個檔案測試。**

   留下欄位順序、意思、分隔符號、可省略的欄位，以及例外處理方式。挑選五個代表性檔案，例如一般檔案、另一個專案的檔案、編號010的項目、日期不明的檔案，以及v02修訂稿。在實際使用的檔案管理工具和接收端應用程式中，檢查名稱顯示、搜尋、排序與重名情況。若省略日期，也要確認剩下的欄位不會被誤讀。先用小範圍找出問題，再決定適用範圍。

重點是一個欄位只表達一種意思。日期有時代表會議日、有時代表儲存日，或同一個數字同時代表項目與修訂次數，都會讓閱讀者需要額外猜測。

## 讓規則容易維持

分隔符號要一致。這個範例在欄位之間使用底線，在日期內使用連字號。英文字母一律小寫，只是本例的編輯選擇，並非所有系統的必要條件。也要確認接收系統允許的字元與檔名長度，避免把單一環境的習慣當成通用規定。

重新命名時保留副檔名。把 `.txt` 改成 `.pdf`，不會讓檔案格式跟著轉換。命名規則也無法取代資料夾結構、存取權限或版本歷程；這些仍要各自管理。適合放在資料夾或另行記錄的資訊，不必全部重複放進檔名。

規則改變時，不要自動替所有封存檔案重新命名。舊名稱可能與連結、引用或其他人的工作流程有關。先決定只套用到新檔案，還是整理經過檢查的一小批既有檔案，再處理遷移範圍。

## 結語

實用的命名規則應該容易說明，也容易重複使用。保留少量欄位、固定順序，並明確定義日期、序號範圍與修訂條件，再用五個實際檔案確認。遇到例外時，先檢查能否簡化規則，而不是不斷增加欄位。

## 常見問題

### 每個檔名都需要日期嗎？

不需要。只有在日期有助於查找或區分檔案時才加入。加入時要說明它代表什麼；日期不明時，不要用今天的日期代替。

### 日期和專案應該哪個在前面？

依主要的查找方式決定。常常跨專案依日期查找，可以先寫日期；想按專案集中顯示，可以先寫專案。專案在前時，日期排序是在各專案內進行。

### v03 代表檔案已經核准嗎？

不代表。它是依約定產生的修訂編號。核准情況需要另外查閱相應的狀態或紀錄。

### Aligna 能做出和範例完全相同的檔名嗎？

目前確認的是八種固定預設，尚未確認能重現本文的完整組合。先檢查是否有符合需求的預設，再於套用前確認預覽。
