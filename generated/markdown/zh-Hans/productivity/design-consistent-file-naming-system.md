# 如何建立一致、好查找的文件命名规则

## 问题

怎样制定一套文件多了也能持续使用的命名规则？

## 简短回答

选用少量含义明确的字段，并始终按固定顺序排列。使用稳定的标识、含义明确的日期、位数统一的序号，以及与批准状态分开的修订编号；写下简短规则和示例，再用五个有代表性的文件测试。

文件名不必容纳全部背景信息。它的作用是让你在列表中认出对象、区分相似文件，并按需要查找。如果每次命名都要重新做很多判断，就值得减少字段或简化规则。

## 先制定一套小规则

“字段”是指文件名中承担一种含义的部分，例如项目标识或日期。命名规则则约定使用哪些字段、各自表示什么、按什么顺序排列，以及用什么符号分隔。下面是人工设计的说明性示例，不代表某个应用支持生成这一组合。

`atlas_2026-10-05_notes_003_v02.txt`

| 字段 | 在本例中的含义 |
| --- | --- |
| `atlas` | 虚构项目 Atlas 的稳定标识 |
| `2026-10-05` | 会议日期，即 2026 年 10 月 5 日 |
| `notes` | 文档类型：会议记录 |
| `003` | 本次会议记录集合中的条目编号 003 |
| `v02` | 已保存修订稿的编号 02 |
| `.txt` | 文件扩展名 |

这一顺序是“项目_会议日期_文档类型_条目编号_修订编号”。003 用于区分集合中的条目，v02 用于区分同一条目的修订稿。两种编号的作用不同，不要让一个数字同时承担这两种含义。

## 推荐流程

1. **把主要查找依据放在前面。**

   如果通常先想到项目名称，就把项目标识放在首位。如果经常跨项目按日期浏览，可以把日期放在首位。采用普通的文本排序时，项目在前的格式会先按项目分组，再在各项目内按日期排列；它不会让所有项目的文件一起按日期排序。先想清楚自己最常问的是“哪个项目”，还是“哪一天”。

2. **同时定义日期格式和日期含义。**

   使用 `YYYY-MM-DD`，年份四位，月份和日期各两位，例如 `2026-10-05`。固定格式可避免简写带来的月、日顺序歧义。还要明确它表示活动日期、拍摄日期还是发布日期，不要在同一字段中混用保存日期和事件日期。如果日期未知，按约定省略该字段，或使用写入规则的未知标记，例如 `unknown`。不要为了填满位置而代入今天的日期。

3. **选择短而稳定的标识。**

   项目简称或记录编号应当持续指向同一个对象。临时负责人姓名、`urgent` 之类的紧急程度描述会随情况变化，不适合作为主要身份标识。若两个项目的简称相似，先规定能区分它们的写法。文件名可能显示在附件列表或共享链接中，因此不要不必要地写入个人信息、客户隐私或机密内容。

4. **明确序号的范围和位数。**

   序号是在整个项目内连续计算，还是每次会议、每批资料重新开始？把范围写清楚。本例中的003只在这次会议的记录集合内使用。`001`、`002`、`010` 这样的补零方式，有助于普通文本排序；采用自然排序的应用可能本来就会按数字大小排列。根据预计数量选择位数。若数量超出原定范围，先规划一致的扩位方式，避免同一范围内混用宽度。

5. **把修订编号和批准状态分开。**

   写明从 `v01` 增加到 `v02` 的条件。例如，可以在保存一份包含新内容、准备送审的修订稿时递增编号。是否每次小改动都递增，或只在形成新的审阅稿时递增，应按工作需要决定并保持一致。`v03` 只说明约定中的修订编号，不能证明文件已经获批。`final-final` 也不能作为批准依据。批准情况应通过单独约定的状态或记录确认。

6. **写下简短规则，并用五个文件测试。**

   记录字段顺序、含义、分隔符、可选字段，以及例外的处理方式。选择五个代表性文件，例如普通文件、另一项目的文件、编号为010的条目、日期未知的文件，以及v02修订稿。在实际使用的文件管理器和接收方应用中检查名称显示、搜索、排序和重名情况。若省略日期，也要确认剩余字段不会被误读。小范围测试通过后，再决定应用到哪些文件。

## 看清四个字段的作用

![用稳定标识确认对象，定义日期含义，统一序号位数，并单独标记修订编号的四个步骤](/blog-assets/zh-Hans/design-consistent-file-naming-system/workflow-diagram.svg)

关键是让一个字段只承担一种含义。日期时而表示会议日、时而表示保存日，或同一个数字既表示条目又表示修订次数，都会让阅读者不得不猜测。

## 让规则容易坚持

统一使用分隔符。本例在字段之间使用下划线，在日期内部使用连字符。英文字母全部小写只是本例的编辑选择，并非所有系统都要求这样做。还要检查接收系统允许的字符和文件名长度，不要把某个环境的习惯当成通用标准。

重命名时保留扩展名。把 `.txt` 改成 `.pdf` 不会转换文件格式。文件命名规则也不能代替文件夹结构、访问权限或版本历史；这些仍需要各自管理。若某项信息放在文件夹或记录中更合适，就不必重复塞进文件名。

修改规则时，不要自动重命名所有历史归档文件。旧名称可能关联链接、引用或他人的工作流程。先决定新规则只用于后续文件，还是用于经过检查的一小批既有文件，再处理迁移范围。

## 结论

一套实用的命名规则应该容易解释，也容易重复使用。保留少量字段，固定排列顺序，明确日期、序号范围和修订条件，再用五个真实文件验证。遇到例外时，先检查能否简化规则，而不是不断增加字段。

## 常见问题

### 每个文件名都需要日期吗？

不需要。只有日期能帮助查找或区分文件时才添加。添加时要明确它表示什么；日期未知时，不要用今天的日期替代。

### 日期和项目应该把哪个放在前面？

按主要查找方式决定。经常跨项目按日期查找，可以先写日期；希望按项目聚在一起，可以先写项目。项目在前时，日期排序是在各项目内部进行的。

### v03 表示文件已经获批吗？

不表示。它是按约定生成的修订编号。批准情况需要另外查看相应状态或记录。

### Aligna 能生成与示例完全相同的文件名吗？

目前确认的是八种固定预设，尚未确认能重现本文的完整组合。检查是否有符合需求的预设，并在应用前查看预览。
