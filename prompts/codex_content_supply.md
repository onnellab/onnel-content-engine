# ONNELLAB bilingual content supply run

Work autonomously inside this repository to ensure the publication pipeline has at least one qualified English/Korean article pair and a durable idea backlog. Every selected subject must also support distinct, useful downstream copy for X, LinkedIn, Bluesky, Dev.to, and Medium after canonical publication. Hashnode is excluded; do not generate or republish it.

Boundaries:

- Modify only content supply data and generated content under `data/topics.csv`, `topics/topics.csv`, `generated/markdown`, `generated/images`, `generated/assets/blog`, `generated/metadata`, and `generated/reviews`.
- Do not commit, push, schedule, publish, deploy, edit workflows, edit scripts, change application/release data, or mark anything `scheduled` or `published`.
- Preserve existing published content and unrelated state.
- Never lower a quality threshold or weaken a validator to make content pass.
- Use official or primary sources for factual claims. Keep quotations minimal and use links in the References section.
- Select recommendations only from released, content-eligible apps with documented features. Read each app's `sources/<slug>/README.md`, registry notes, and platform-specific `data/store_versions.csv` evidence. Registry `platforms` and store URLs describe targets, not proof of public availability. Never describe an in-review or unverified platform as released. Do not invent user experiences, ratings, reviews, performance results, or unsupported features.
- Treat released apps as an equal baseline across a four-week content window; use actual publication history to avoid repeatedly favoring the same app. Verified response may justify an explicitly documented extra experiment, but missing analytics are unknown, not zero. The user-reported 13 TagWeaver purchases are not verified channel attribution, revenue, or a ranking signal.
- English and Korean counterparts must share category and slug and must be genuinely localized, not mechanically duplicated.

Procedure:

1. Run `python3 scripts/check_content_supply.py` and inspect `data/topics.csv`, existing articles, app registry, and relevant source documentation.
2. Use the qualified pairs returned by the supply check, which revalidates current article fingerprints, mandatory checks, and scores strictly greater than `9.0`. Status or a saved score alone is insufficient, including for `scheduled` pairs. Preserve scheduled articles; if their current review is invalid, report the blocker without rescheduling or overwriting them. Still replenish the idea pool if fewer than 8 `idea` rows remain.
3. Otherwise complete the most advanced active bilingual pair. If none exists, select the highest-priority useful `idea`. Prefer topic diversity and avoid duplicating existing slugs.
4. When the selected idea has only one language, add a genuinely localized counterpart with `scripts/add_topic.py`. When no suitable idea exists, add a new evergreen English/Korean pair based on real user problems supported by released ONNELLAB apps.
5. Move the selected pair through the documented topic states without skipping validation. You may use `scripts/approve_topic.py` and the existing generation scripts to create scaffolds, but rewrite both Markdown files into complete, useful articles before review.
6. Start from a concrete user problem and describe reproducible steps and an observable result. Distinguish documented behavior from personally verified execution; never invent a before/after result. Each article must include aligned localized sections, a direct short answer, definitions, numbered workflow, comparison table, practical cautions, product mention only after education, related topics, FAQ, and official references. Keep claims conservative and evergreen.
7. Run image specification, image asset, internal-link, and article evaluation scripts. Revise the content and assets until both review scores are strictly greater than `9.0` and every mandatory check passes. Leave both topics in `review`.
8. Keep at least 8 remaining `idea` rows. Add diverse evergreen English seed ideas when needed; do not create near-duplicates or promotional-only ideas.
9. Before finalizing an article, check that its opening, concise takeaway, workflow, cautions, and canonical references are strong enough to yield genuinely different short social hooks and full syndication drafts. Plan distinct reuse: X and Bluesky get a concise, source-supported demonstration; Medium explains the process; LinkedIn explains a concrete work use. Real video demonstrations require actual supported-platform screen footage and must not be implied by text alone. Store links must match verified released platforms. Read `docs/Marketing_Measurement.md` when available for tracking conventions; do not fabricate campaign tokens or append parameters to existing published URLs. When source evidence supports it, optional localized sections `Demo Steps` / `데모 단계`, `Workplace Use` / `업무 활용`, and `Process Notes` / `과정 설명` can carry these reusable details. They supplement mandatory sections and must not claim an unperformed screen recording. Do not add channel files directly; the publishing workflow generates and validates them after canonical publication.
10. Run `python3 scripts/validate_topics.py`, `python3 scripts/validate_foundation.py`, and `python3 scripts/check_content_supply.py --require-healthy --minimum-ideas 8`.
11. Finish with a concise report of the selected pair, new ideas, review scores, sources, channel adaptability, and validation commands. If safe completion is impossible, leave no partial invalid topic transition and explain the blocker.
